# Redshift × AWS Backup｜調査報告書（公開Markdown版）

# 11. RPO

RPO（Recovery Point Objective）は、どれだけ過去までのデータ損失を許容するかという目標。例えば目標1時間は、「障害直前1時間分までの損失を業務が許容できるか」という判断であり、1時間ごとの設定だけで保証が成立するわけではない。

| **区分**            | **公式仕様または評価方法**                                       | **設計で確認すること**                         |
|---------------------|------------------------------------------------------------------|------------------------------------------------|
| Provisioned標準自動 | 約8時間または5GB/node、指定schedule最短1時間 \[S07\]             | 実取得時刻、失敗、負荷、保持、正常性           |
| Serverless標準RP    | 約30分または5GB/node、一定容量以上で最短15分、24時間保持 \[S08\] | 変更条件と実生成点。任意時刻PITRではない       |
| AWS Backup          | Rule時刻、開始window、完了window \[S38/C061\]                    | 予定、実開始、snapshotデータ時刻、完了を別記録 |
| 攻撃検知            | 公式の一律保証値なし                                             | 改ざん開始時刻と認識までの時間                 |
| 最後の正常点        | 実データ照合で選ぶ復旧点                                         | 直近のRPがすでに改ざん済みでないか             |
| 変更量              | 取得条件や処理時間、保存量へ影響                                 | 物理block更新、再書込、日次バッチ集中を測定    |

【設計上の解釈】突然の故障では「障害時刻−最後に復旧できたデータ時刻」を観測損失幅とする。ランサムウェアでは「障害/攻撃の評価時刻−最後の正常な復旧点のデータ時刻」が長くなる。完了時刻をデータ時刻として代入しない。検知が遅ければ、頻繁なsnapshotでも正常世代が保持外となり得る。

【推定】毎日1回、処理/検知遅延なしという単純条件なら取得間隔は24時間。しかし実運用のRPOへは取得失敗、開始window、正常点の選別、コピー遅延等を加味する。「RPO=24時間保証」と記載しない。

## RPO試験の期待状態

| **時点** | **操作**                                         | **復旧後に検証する事実**                 |
|----------|--------------------------------------------------|------------------------------------------|
| T0       | 基準表id=1, amount=100をcommitしBackup完了を確認 | T0 snapshotが基準1行を含む               |
| T1       | id=2, amount=200を追加・commit                   | T0へ戻すならid=2がない                   |
| T2       | id=1のamountを999へ更新・commit                  | T0へ戻すならamount=100                   |
| T3       | 障害を想定し時刻記録                             | 本番削除はしない。最終正常点を選択       |
| T4       | 専用復旧先へRestore                              | 件数、値、view、権限、再処理の要否を判定 |

【実環境確認事項】この試験で測った値は、当該データ量・負荷・構成・時点での観測結果。AWS保証値へ一般化しない。

# 12. RTO

RTO（Recovery Time Objective）は、業務をいつまでに戻すかという目標。AWSのRestore Jobが完了しても、データが正しい、BIが接続できる、業務を再開できるとは限らない。今回参照した公式情報に一律のRedshiftバックアップ復旧時間保証は確認できない。

| **時刻** | **工程**           | **証跡/責任**                         |
|----------|--------------------|---------------------------------------|
| 障害発生 | 実際に影響が始まる | 監視/業務ログ。分からない場合は未確定 |
| T0       | 障害認識           | 通知・受付時刻                        |
| T1       | 復旧判断           | 責任者の判断、隔離/封じ込め完了条件   |
| T2       | Recovery Point選択 | 最後の正常点の根拠、RP/snapshot ID    |
| T3       | Restore開始        | StartRestoreJob送信、Job ID           |
| T4       | AWS Restore完了    | Job成功とresource ready。eventも突合  |
| T5       | データ確認完了     | 件数・値・集計・permissionの記録      |
| T6       | 接続確認完了       | endpoint、BI/ETL、代表クエリ          |
| T7       | 業務再開可能       | 業務責任者の判断、残作業と制限        |

| **時間指標**         | **式**      | **意味**                              |
|----------------------|-------------|---------------------------------------|
| AWS Restore処理時間  | T4−T3       | AWSへ開始を依頼してから完了までの観測 |
| 技術復旧時間         | T6−T0       | 認識からデータ・接続確認完了まで      |
| 業務復旧時間         | T7−T0       | 認識から業務再開可能まで              |
| 障害発生から業務再開 | T7−障害発生 | 検知遅延も含めた全影響時間            |

【実環境確認事項】07_RPO_RTOシートにUTC日時を入力すると分へ換算。未入力は空欄のまま、逆順はエラー表示。復旧先の保持/検証のために設定した「稼働8時間」は費用上の仮定であり、RTOではない。

【AWS公式仕様】RA3復旧ではManaged Storageを参照し、通常クエリを通じたキャッシュが利用される。利用可能となった直後の業務性能も確認する。\[S09\]

【設計上の解釈】RTOを短くする候補は、復旧先のquota/NW/role/鍵の事前準備、metadataの保存、正常点判定用の照合、接続切替手順の標準化。短縮効果は実測で評価し、根拠のない「数分で業務復旧」を予算資料に入れない。

# 13. 業務影響

| **業務**          | **一般的な影響**                       | **AWS仕様から生じる確認点**                         |
|-------------------|----------------------------------------|-----------------------------------------------------|
| BI/ダッシュボード | 画面更新停止、過去値表示、意思決定遅延 | 新cluster endpointへの切替、認証、権限、クエリ性能  |
| 分析業務          | アドホックSQLや機械学習用抽出停止      | DB/schema/view、外部データ参照、IAMを確認           |
| レポート作成      | 日報/月報の遅配、数字の不一致          | 復旧点のデータ時刻とレポート基準時刻を整合          |
| 日次処理          | 取込・変換・集計の欠落/再実行          | T0以降の原本を再ロードできるか。重複排除を確認      |
| 月次処理          | 締め処理遅延、監査証跡の不整合         | 月次/年次snapshotの正常性と保持を事前に証明         |
| バッチ/ETL        | 依存ジョブの失敗、下流へ誤データ配布   | Redshift外のジョブ設定/コード/credentialは別保護    |
| データ再ロード    | 原本再収集、取込時間、追加Compute      | S3/COPY権限、原本鍵、ネットワーク、入力量           |
| 再集計            | 中間表/集計表の再生成、数値検証        | 単一表Restoreで戻らないview/grant等を再設定         |
| 外部システム連携  | 接続エラー、二重配信、欠損             | endpoint、DNS、connection pool、watermark、再送設計 |

【設計上の解釈】損失影響は時間だけでは決まらない。最重要レポートの締切、再取得不能データ、外部配布済みの誤集計、バッチの冪等性を業務責任者と確認し、RPO/RTO目標を設定する。一般的な業務影響と、AWSが復元するresource/設定の範囲を混同しない。

# 14. 費用体系

## 14.1 Redshiftの課金

| **区分**              | **課金単位/対象**                                 | **本試算での扱い**                                  |
|-----------------------|---------------------------------------------------|-----------------------------------------------------|
| Compute / Provisioned | USD/node-hour                                     | node単価×総node数×稼働時間。予約割引なし            |
| Compute / Serverless  | USD/RPU-hour                                      | 実使用RPU-hour。最低課金/秒単位の仕様に注意         |
| Managed Storage       | USD/GB-month                                      | 通常保存量と復旧先追加量を分離                      |
| Snapshot Storage      | USD/GB-month                                      | 有料manualの保存集合。標準/Backupを二重計上しない   |
| 標準Backup関連        | 自動最大35日、標準RP24時間の無料保護              | 無料分をmanualの有料保存へ加算しない                |
| Data Transfer         | USD/GB transferred                                | native Cross-Region等の標準転送。Data Sharingとは別 |
| その他                | Concurrency scaling、Spectrum、ML、ネットワーク等 | 本モデルで自動加算せず必要に応じ別見積              |

【AWS公式仕様】2026年6月8日からServerless/RGのmanual snapshotはaccount内のunique blockに基づく新しい料金説明。RA3は既存のS3段階料金を継続。古いDC/DSの無料snapshot容量枠をRA3/Serverlessへ流用しない。標準の無料自動保護とmanual料金を混同しない。\[S23、S28、S29\]

## 14.2 AWS Backupと関連サービス

【AWS公式仕様】独立したAWS Backup管理の対象ではないresourceの保管は、元service側に課金される。Redshiftでは元snapshotの保管費として計算し、AWS Backupの一般Warm/Cold/Restore単価を重ねない。Vault Lock自体の追加料金はないが、保護期間中の保存料金は発生する。\[S18、S19、S22、S24\]

| **AWS Backup区分**                  | **Redshift適用と料金モデル**                               |
|-------------------------------------|------------------------------------------------------------|
| Backup/Warm Storage                 | Redshift Snapshot Storage側に含める                        |
| Restore                             | 一般\$/GB料金を流用せず復旧先Compute/RMSを計上             |
| Cross-Region / Cross-account Copy   | SS対象外、Provisioned未確認。AWS Backup Copy料金は未計上   |
| Cold / retrieval / Air-gapped       | SS対象外、Provisioned未確認。採用対象外として未計上        |
| Vault/Lock                          | 管理料金を独立加算しない。Lock満了までの保存増を計算       |
| Audit/検索/自動Restore testing等    | 固有対応がない/未確認の機能は費用へ加算しない              |
| 関連KMS/CloudTrail/S3/Organizations | 鍵・要求・ログ保管・独立原本等を別集計。必要費用は追加入力 |

# 15. 費用試算

## 15.1 増分保存モデル

【推定】入力Dは圧縮後の物理データ容量、cは物理blockが1日に更新される割合、fは1日あたりの有料manual取得回数、Rは日次系保持日数、M/Yは月次/年次の保持世代数。データ容量一定、均等かつ独立したblock更新を仮定し、データ増加・縮小・特殊な再書込は含めない。

【推定】g日離れた2つの保持点の差分割合を q(g)=1−(1−c)^g と近似。保持点の年齢を現在から順に並べ、同時点は統合。有料保存容量 B=D＋Σ\[D×q(隣接する保持点の間隔)\]。日次系はn=f×R世代、月次は30日間隔、年次は365日間隔。取得の有効な点がなければB=0。

【設計上の解釈】同じblockが何度更新されても、異なる保持点が必要とする過去versionは残る。「全期間の更新済みblock率を1回だけDに足す」方法では長期保持を過小評価し得る。一方、各snapshotをDとして足す方法では共通blockを重複計上する。04_Backup容量に保持点ごとの中間計算を表示し、測定された平均GBを入力すれば近似値を置換できる。

【未確認】日次変更率と世代数だけでは請求容量を厳密に決められない。圧縮、ブロック再利用、データ増減、再フル、保持集合、取得失敗により変わる。公式ブログの90日・5%の容量例は導出が明確でないため、その数値を転載せず本モデルの仮定を明示した。\[S29、D05、D06\]

| **費用**        | **式/入力**                                                              |
