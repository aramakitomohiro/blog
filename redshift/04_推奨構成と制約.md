# 16. 推奨構成

3案は【設計上の解釈】による提案。AWS公式の個別仕様/保護機能を組み合わせたもので、AWSがこの3案やRPO/RTO値を推奨・保証しているという意味ではない。

| **項目**   | **A. 最小構成**                                    | **B. 標準構成**                                                      | **C. 耐性重視構成**                                                   |
|------------|----------------------------------------------------|----------------------------------------------------------------------|-----------------------------------------------------------------------|
| 構成       | 標準自動snapshot/RP＋重要作業前manual、IAM、鍵監視 | A＋AWS Backup日次manual、必要な月次/年次、Vault Lock、監査、復旧訓練 | B＋検証済native別Region経路、別管理の原本/UNLOAD・DDL・鍵による再構築 |
| 目的       | 誤操作・短期障害から復旧                           | 長期保持と削除統制、継続監査                                         | 元account/鍵を失うシナリオも評価                                      |
| メリット   | 最小の追加保管・運用                               | 保持/失敗監視を標準化、Complianceで削除耐性                          | 管理境界・保存場所・鍵依存を分離可能                                  |
| デメリット | 管理者削除や24h超潜伏に弱い                        | Lock費用拘束、role/Vault管理、鍵依存は残る                           | 再ロードはsnapshotと同じ機能/RTOではない。費用と運用増                |
| 想定RPO    | 公式取得頻度を基に要件設定。保証値なし             | 保護manualは例：日次24h＋遅延。短期は標準を使用                      | コピー/原本出力頻度＋遅延。経路別に測定                               |
| 想定RTO    | 未設定、実測で決定                                 | 未設定、全体/表の復旧訓練で決定                                      | 未設定、snapshot復旧と再構築を別測定                                  |
| コスト影響 | manual保存と復旧試験分                             | 長期manual容量、KMS/監査、消せない保持期間                           | 転送、先保存、S3要求、別account資源、再ロード                         |
| 対象脅威   | 誤削除、resource障害                               | RP削除、通常管理者侵害の一部                                         | 広いaccount/鍵侵害、Region障害の影響分離                              |
| 運用負荷   | 小                                                 | 中                                                                   | 大、独立管理責任者と復旧訓練が必要                                    |

【設計上の解釈】Bの例示保持35日/月次12/年次7は費用モデルを説明するための入力例。業務・規制・正常性の検知期間から保持を決め、無条件に7年保持を推奨しない。Compliance固定前に、短期のGovernance検証、復旧成功、保持条件と費用を確認する。\[S19\]

【設計上の解釈】CにAWS Backup Air-gapped vaultや未確認のCopyを描かない。native共有のみでも独立性は不十分。原本を別管理S3でObject Lockする場合、S3の保持モード、書込/削除権限、暗号鍵、ログ、復元資源を別設計し、元accountの権限を失った条件で再構築できることを実証する。\[S16、S50–S52\]

# 17. 制約事項

| **課題** | **公式情報/環境の不足**                                                 | **当面の判断**                                                                    |
|----------|-------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
| D01      | Serverless BackupSelectionのsnapshot ARN例とnamespace保護説明が不一致   | namespaceArnをget-namespaceから取得し、実選択と定期取得を試験                     |
| D02      | 現行feature tableにProvisioned Redshiftの行がない                       | copy/Cold/Air-gapped/Audit Manager固有対応をAWS Supportへ照会。確認前は採用対象外 |
| D03      | Redshift鍵削除後の特別backup復旧記述は一般KMS削除仕様との関係不明       | 利用鍵・特別backupの暗号鍵・復旧期限/条件をAWS Supportへ照会                      |
| D04      | Backup文書のnew cluster表現とnative表復旧の元cluster限定が不一致        | native固有制限を優先。BackupのTABLE_RESTORE実挙動を検証                           |
| D05      | 日次変更率から課金unique block容量を厳密には導出できない                | 固定容量・独立block更新仮定を実測平均GBで補正                                     |
| D06      | 公式ブログの90日5%で14.5 TBという容量例は導出不明                       | その数値を転載せず独立計算と実測を使用                                            |
| D07      | AWS Backup管理manual snapshotへnative自動copy設定が作用する範囲が未確認 | 独立したnative snapshotでコピー経路を先に確認。managed RPの扱いを照会/試験        |
| D08      | 種類、容量、変更率、NW、RPO/RTO要件、承認者が未入力                     | Phase0で値を採取し費用入力・検証対象へ反映                                        |
| D09      | 本成果物作成時点ではAWS account操作・Restore・請求測定を未実施          | Phase0〜12を実施し実結果と証跡を記録                                              |
| D10      | Snapshot共有だけでは管理者/account侵害への独立性不足                    | C案では別管理の原本/S3 Object Lockと再ロード経路を設計                            |
| D11      | 固有資料に壊れたCLIテンプレート・Consoleラベル差あり                    | 最新CLI参照とget-recovery-point-restore-metadataを使用                            |
| D12      | 資料完成と本番採用完了は別                                              | 要件充足・残余リスク・予算・運用引継ぎを決裁                                      |

【未確認】公式ページ相互の相違は、(1)Serverless Selectionのsnapshot ARN例、(2)Provisioned機能表の行欠落、(3)鍵削除後の特別backup説明、(4)表Restoreの新cluster表現、(5)一部CLIテンプレートの書式、(6)料金ブログ例の容量導出。根拠一覧の備考と課題D01〜D07/D11で追跡する。

【AWS公式仕様】一般KMS仕様では、通常の対称CMKが永久削除された後、その鍵で暗号化されたデータは復号できない。Redshift暗号化資料には鍵利用不能時の14日や特別backupに関する説明があるが、通常snapshotが削除済鍵を不要にして復旧できるという一般保証にはできない。\[S31、S32\]
