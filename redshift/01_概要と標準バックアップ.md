# 1. Executive Summary

【AWS公式仕様】Amazon RedshiftはAWS Backupの保護対象。Provisionedはクラスター、Serverlessはnamespaceを対象に、Redshiftの手動スナップショットをAWS Backupが管理する。標準の自動スナップショットとServerlessの標準Recovery Pointは、AWS Backup管理のRecovery Pointとは別の仕組み。\[S01–S04\]

【設計上の解釈】導入効果の中心は、取得計画・保持・ジョブ・監査の一元化と、Vault Lockを使った保持中の削除保護。バックアップの中身、元データの正常性、元KMS鍵の可用性、業務再開までの時間は、AWS Backupを追加するだけでは解決しない。\[S18–S20、S31\]

| **設計判断** | **結論**                                                | **採用条件**                                                |
|--------------|---------------------------------------------------------|-------------------------------------------------------------|
| 基本保護     | 標準自動保護＋必要期間のmanualを確保                    | 最後の正常点を識別し、全体/表の復旧を実証                   |
| AWS Backup   | 両形態で利用可能。Recovery Pointの実体はmanual snapshot | 元ARN、snapshot ARN、Job、Vaultを実環境で突合               |
| 強い削除防止 | Complianceの猶予期間後に保護を固定                      | Governance解除可能性、KMS、保持満了、アカウント閉鎖を別評価 |
| 高度な機能   | ServerlessのCopy/Cold/Air-gapped等は対象外              | Provisionedは現行機能表の行欠落により固有対応を未確認扱い   |
| 本番採用     | B案を条件付きの基本候補                                 | 必須検証、費用実測、残余リスクの受入れ後に決裁              |

【推定】東京の例示構成はRA3.xlplus×2、720時間/月、データ1,024 GB、物理block日次変更率5%、日次35日・月次12世代・年次7世代。有料snapshot保存量は定常時約16,730.78 GB、snapshot費約418.27 USD/月。通常Compute、RMS、月1回の復旧先8時間、追加KMSを含む既知費用小計は約2,307.09 USD/月。これは初年度の保存推移や最終請求額を保証する値ではない。

【未確認】対象AWS環境、RPO/RTO要件、実変更率、必要権限、転送実績は未提供。架空の試験成功・RTO値を置かず、入力欄と課題D08/D09に残した。

根拠：\[S01\]、\[S02\]、\[S18\]、\[S19\]、\[S23\]、\[S25\]

# 3. 結論

## 3.1 確定した技術関係

| **対象**                     | **役割・関係**                                                            | **分類／根拠**             |
|------------------------------|---------------------------------------------------------------------------|----------------------------|
| Provisioned cluster          | バックアップ対象となるデータウェアハウス。RA3はnode種類                   | AWS公式仕様／S01、S03      |
| RA3 / Managed Storage        | 計算資源と保存領域を分離。RMS自体をBackup Selectionで選ぶ構造ではない     | AWS公式仕様／S33           |
| Serverless namespace         | DB・ユーザー・データ等をまとめた保護対象。workgroupは主に計算/NW側        | AWS公式仕様／S04、S35      |
| Redshift manual snapshot     | AWS Backupが取得・管理するバックアップの実体                              | AWS公式仕様／S01           |
| AWS Backup Recovery Point    | 復旧対象として管理されるsnapshotとそのメタデータ                          | AWS公式仕様／S01、S05、S06 |
| Backup Vault                 | Recovery Pointの管理単位。利用者のS3バケットではない                      | AWS公式仕様／S20、S58      |
| Serverless標準Recovery Point | Redshiftが自動生成する24時間の復旧点。AWS Backup Recovery Pointとは異なる | AWS公式仕様／S08           |

## 3.2 本番判断

【設計上の解釈】標準構成Bを候補とする。短期の細かな戻しは標準保護、長期の統制された保管はAWS Backup、業務再開は定期復旧訓練で担保する。管理者侵害まで求める場合は、Complianceの削除耐性に加え、別管理の鍵・原本・構成情報からの独立再構築をC案として設計する。

【未確認】現行AWS Backup feature availabilityにはProvisioned Redshiftの個別行が見当たらない。この欠落から「Provisionedは非対応」と結論することも、「すべての高度機能が使える」と結論することもできない。基本Backup/Restoreは固有資料で対応を確認し、Copy/Cold/Air-gapped等は未確認として採用対象から外す。\[S01–S06\]

【実環境確認事項】本番採用は現時点で保留。RPO/RTO、正常性、削除拒否、鍵の継続利用、監査、実料金の証跡をもって最終判定する。

# 4. Amazon Redshift概要

【AWS公式仕様】Amazon Redshiftは分析用のデータウェアハウス。大量データをSQLで集計し、BI、分析、レポートに利用する。Provisionedはnode構成を指定したclusterを運用し、Serverlessはnamespaceとworkgroupを分けて管理する。\[S34、S35\]

| **概念**             | **初学者向けの説明**                            | **バックアップ設計への影響**                                 |
|----------------------|-------------------------------------------------|--------------------------------------------------------------|
| Provisioned          | 必要な大きさの計算用nodeを選ぶ方式              | 復旧先のnode、quota、subnet、SG、parameterを準備             |
| RA3                  | 計算とデータ保存を分離するnode系列              | nodeを増減してもRMSとsnapshotの課金を別に考える              |
| Managed Storage      | 頻繁に使うデータをSSD、その他をS3に置く管理領域 | 利用者管理のS3 bucketではなく、Object Lockを直接設定できない |
| Serverless namespace | データ・DB・ユーザーをまとめる器                | AWS Backupの保護単位。全体復旧は既存namespace上書き          |
| Serverless workgroup | 計算能力、endpoint、ネットワーク等の設定        | namespaceを戻すだけで接続/性能が元どおりとは限らない         |
| 可用性・耐障害性     | 設備/AZの障害時にサービスを継続・回復する性質   | 意図しないDELETEや改ざんを過去へ戻す能力とは区別             |

【AWS公式仕様】Multi-AZは複数AZで高可用性を提供し、対応する障害シナリオではゼロRPOを説明する。ただし、論理削除・不正更新・鍵喪失に対する「バックアップRPO=0」の保証ではない。Multi-AZの追加Computeもバックアップ保存費とは別。\[S23、S36\]

【設計上の解釈】保存基盤の耐久性が高くても、正規権限によるDELETEは業務データとして反映され得る。可用性、過去世代、削除耐性、鍵の独立性を別々の設計項目にする。

# 5. Redshift標準バックアップ

## 5.1 Provisionedの比較

| **項目** | **Automated Snapshot**                                 | **Manual Snapshot**                       | **Recovery Point**               | **備考**                     |
|----------|--------------------------------------------------------|-------------------------------------------|----------------------------------|------------------------------|
| 作成主体 | Redshift自動・設定schedule                             | Console/API/CLI、またはBackup管理         | Serverless標準の同名機能は対象外 | Backup RPは7章               |
| 頻度     | 通常約8時間または変更5GB/node。指定scheduleは最短1時間 | 必要時または計画で取得                    | 対象外                           | 生成時刻・完了遅延は実測     |
| 保持     | 既定1日。RA3は1〜35日、無効化不可                      | 既定無期限、指定保持可能                  | 対象外                           | 手動APIの1〜3653日/−1と確認  |
| 削除条件 | 保持期限、cluster削除等でサービスが削除                | 期限または権限者削除。cluster削除後も残る | 対象外                           | 自動を長期保管の代用にしない |
| 保存方式 | 初回後は変更データを増分保存                           | 同じく増分snapshot                        | 対象外                           | 世代数×毎回フルではない      |
| 料金     | 標準の自動保護は最大35日無料                           | 有料snapshot storage                      | 対象外                           | RA3はS3段階料金              |

【AWS公式仕様】データ変更条件による自動取得と、明示したscheduleは別の説明。5GB/nodeを超える大きさでは最小15分の制約が示されるが、「必ず15分ごとに取得する」という設定ではない。手動snapshotは削除しても他のsnapshotの復旧に必要なデータを保持する増分管理。保持期限のあるsnapshotを消しただけで、その論理サイズ分がすべて課金から消えるとは限らない。\[S07、C010\]

## 5.2 Serverlessの比較

| **項目** | **Automated Snapshot**                        | **Manual Snapshot**                        | **Recovery Point**                               | **備考**                       |
|----------|-----------------------------------------------|--------------------------------------------|--------------------------------------------------|--------------------------------|
| 位置付け | Provisionedと同じ自動snapshot保持設定は対象外 | 長期保持用の明示snapshot                   | Serverless標準の短期自動復旧点                   | 3種の語を流用しない            |
| 取得     | 標準自動保護は右欄RP                          | Console/API/CLI、snapshot schedule、RP変換 | 約30分または変更5GB/node。一定容量以上で最短15分 | RP取得schedule変更不可         |
| 保持     | 該当なし                                      | 1〜3653日、または無期限                    | 24時間                                           | 期限を延ばす場合manualへ変換   |
| 削除     | 該当なし                                      | 期限または権限者削除                       | 24時間の保持範囲で自動管理                       | namespace削除条件は事前確認    |
| 料金     | 該当なし                                      | unique blockの有料保存                     | 標準24時間分は無料                               | 2026-06-08の料金更新           |
| 管理     | 該当なし                                      | RedshiftまたはAWS Backup                   | Redshift                                         | AWS Backupで既存RPを管理しない |

## 5.3 コピー、共有、暗号化、復旧

| **機能**      | **Provisioned**                             | **Serverless**                              | **設計上の留意点**                                     |
|---------------|---------------------------------------------|---------------------------------------------|--------------------------------------------------------|
| Cross-Region  | nativeの自動/manual copy。コピー先は同時1つ | snapshotと標準RPをnativeでcopy。先は同時1つ | Regionを変える操作。先の保管費、転送、KMS、遅延を確認  |
| Cross-account | manual snapshotの共有と復旧                 | snapshotの共有と権限解除                    | accountを変える操作。共有は所有権移転ではない          |
| 暗号化        | snapshotは元の暗号化を利用                  | 同様に元データの鍵を継承                    | CMKの状態・key policy・grantを管理                     |
| 全体Restore   | 新clusterへ全DB。稼働clusterへの巻戻し不可  | 既存namespaceに復旧しデータを上書き         | Serverlessは復旧専用namespaceを準備                    |
| 単一表Restore | 元の稼働clusterへ別名の新表                 | 同型の復旧経路で新しい表を作成              | 既存表の上書き、異種間表復旧、interleaved sort等に制約 |

【AWS公式仕様】Provisionedで共有されたsnapshotは、共有先がdescribe/restoreできる一方、共有先によるcopy/deleteは不可。所有元はアクセスを取り消せる。所有元アカウントがinactiveの場合は新たな復旧ができない。共有解除やKMS権限喪失に依存するため、共有だけをランサムウェア対策の独立コピーと数えない。\[S16、S17\]

【AWS公式仕様】Serverlessのコピー先Recovery Point保持は1日固定。snapshotコピーの保持は指定可能。元と先のRegionのKMS/grantを確認する。AWS Backup管理manualにnative自動copyがどこまで作用するかは公式説明だけで確定できず、D07で別検証。\[S14、S15\]

【設計上の解釈】標準自動保護は短期の誤操作復旧に有用。manualは任意時点・長期保管に有用。ただし手動削除を許された管理者には弱く、通常の保持設定だけでイミュータブルにはならない。RTOは保存方法の名前だけで決まらず、復元容量・構成・データ検証・業務接続に依存。
